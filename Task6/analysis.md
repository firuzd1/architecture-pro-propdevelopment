# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
    - Кто: system:serviceaccount:secure-ops:monitoring
    - Где: namespace kube-system
    - Почему подозрительно: сервисный аккаунт monitoring не должен иметь доступа к секретам kube-system. это попытка получить токены других сервисов и потенциально захватить кластер

2. Привилегированные поды:
    - Кто: system:serviceaccount:secure-ops:monitoring через escalate-binding
    - Комментарий: под privileged-pod запущен с securityContext.privileged=true, что даёт полный доступ к хосту. такой под может читать файлы ноды, монтировать файловую систему и выходить за пределы контейнера

3. Использование kubectl exec в чужом поде:
    - Кто: system:serviceaccount:secure-ops:monitoring
    - Что делал: выполнял команды внутри пода coredns в namespace kube-system, читал /etc/resolv.conf. это разведка сетевой конфигурации кластера

4. Создание RoleBinding с правами cluster-admin:
    - Кто: система от имени monitoring serviceaccount
    - К чему привело: сервисный аккаунт monitoring получил права cluster-admin через escalate-binding, что означает полный контроль над кластером без ограничений

5. Удаление audit-policy.yaml:
    - Кто: под именем admin
    - Возможные последствия: попытка отключить аудит чтобы скрыть следы атаки. без audit-policy дальнейшие действия злоумышленника не будут логироваться

## Вывод

В кластере зафиксирована последовательность действий характерная для атаки с эскалацией привилегий:
1. сначала разведка — доступ к секретам и exec в чужой под
2. затем эскалация — создание привилегированного пода и rolebinding с cluster-admin
3. попытка заметания следов — удаление audit-policy

Основная ошибка политики RBAC — сервисный аккаунт monitoring изначально имел слишком широкие права, что позволило провести атаку. Рекомендуется ограничить права всех сервисных аккаунтов по принципу минимальных привилегий.
